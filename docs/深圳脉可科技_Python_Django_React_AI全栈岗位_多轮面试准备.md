## 2. 贯穿全场的项目故事

### 60 秒版本

我独立开发了一套联邦 Text2SQL 系统，让业务人员可以用自然语言查询单库或多源数据。系统使用 LangGraph 编排意图识别、语义记忆、Schema 检索、SQL 生成、校验、评审、执行和分析节点；FastAPI 提供接口，React 构建对话和监控页面，DuckDB 完成联邦查询。  

为了让它不只是 Demo，我继续补充了 SQL 只读与 AST 校验、表列级权限、租户隔离、会话记忆、Token 和耗时监控、黄金用例评测、SSE 状态事件、本地有界队列、Redis Streams 持久任务、独立 Worker，以及 Docker Compose 部署。这段经历让我掌握了 AI 应用从模型能力到业务系统落地的完整链路。

### 120 秒版本

项目最初要解决的问题是：业务人员不懂 SQL，但需要查询分散在不同数据源中的订单、用户行为和特征数据。直接让大模型生成 SQL 会遇到三个问题：Schema 太大、SQL 可能不安全、模型或数据库失败后无法恢复。

我用 LangGraph 把流程拆成多个有明确职责的节点。先通过规则优先、LLM 兜底识别意图；查询类请求再检索语义记忆和实时 Schema，只召回相关表；SQL Agent 生成候选，Validator 做单语句、只读、行数和 AST 校验，Reviewer 检查表字段、关联关系和执行计划，Executor 才能执行，最后 Analyst 基于真实结果生成报告。失败会根据错误类型回到 Schema 和 SQL 生成链路，最多重试两次。

工程层面，FastAPI 接口支持 request ID、幂等键、统一错误、健康检查、RBAC、表列权限和审计。长任务既可以使用进程内有界异步队列，也可以使用 Redis Streams 持久化，由独立 Worker 消费；后端提供状态、结果、暂停和 SSE 事件接口。Docker Compose 会拉起 API、Worker、Redis 和 PostgreSQL，前端通过多阶段构建进入运行镜像。这个项目让我形成了一个比较完整的 AI 系统开发方法：模型负责不确定性判断，确定性代码负责权限、安全、状态和交付。

| P1 / JD 推演题 | 需求很急，如何用 Vibe Coding 快速交付但避免 AI 劣质代码？ | AI 编程、工程纪律 | 小任务、小 diff、测试、边界审查 | 我会先让 AI 阅读仓库规范和相关调用链，再把需求拆成边界明确的小改动。AI 可以辅助检索、脚手架、测试和重复重构，但数据模型、权限、幂等、费用和发布判断必须由开发者负责。每次改动控制 diff，执行单测、静态检查和接口回归，关键逻辑做人审。我的项目从原型迭代到队列、RBAC、评测和 Docker 时，就是按模块补测试，而不是一次性让 AI 重写系统。 | AI 写过什么 Bug？如何检查依赖幻觉？ | “大部分代码都是 AI 写的，我只负责运行”；没有验证闭环 |

## 5. 三面/终面：证明有 Owner 意识和成长潜力

**面试官假设：** 部门负责人、创始团队或最终用人负责人。  
**核心判断：** 是否理解产品目标，能否在资源有限时做取舍，能否长期承担核心模块。  
**回答重心：** 业务结果、边界意识、优先级和长期成长。

| 优先级 / 来源 | 高概率题 | 考察点 | 回答思路 | 可直接开口答案 | 追问预判 | 危险表达 |
| --- | --- | --- | --- | --- | --- | --- |
| P0 / JD 推演题 | 两周内做一个 AI 短剧 MVP，你怎么取舍？ | 优先级、交付能力 | 先闭环，再自动化；明确不做什么 | 两周目标不是做完整平台，而是跑通一个可验证闭环：创建项目、输入主题、生成剧本、人工确认分镜、提交视频任务、查看进度并下载作品。第一周完成数据模型、Django API、任务队列和最小 React 页面；第二周接模型、补错误处理、权限、日志和部署。第一版暂不做复杂多人协作、自动发布和多模型动态路由。先让一条链路稳定、有指标，再根据用户反馈扩展。 | 哪个环节风险最大？如何验收？ | 什么都答应；只列技术任务，不定义用户结果 |
| P0 / 相似题迁移 | 项目中最难的问题是什么？你怎么解决？ | 复盘、问题解决 | 从“同步 Demo”到“可恢复任务系统” | 最难的不是 SQL 生成，而是把长时间、不稳定的模型调用变成可管理的请求。早期同步执行会阻塞，请求取消也只在单进程有效。我先加入本地有界队列和 SSE 状态，再增加 Redis Streams 持久任务与独立 Worker，用 request_id 做幂等，补充状态、结果、暂停、重试和健康检查。最后通过 Docker Compose 把 API、Worker、Redis 和 PostgreSQL 固化。这让我认识到 AI 产品的核心竞争力不仅是模型效果，也包括任务状态和故障恢复。 | Redis 挂了怎么办？还有什么没解决？ | 说“没有遇到困难”；只归因于第三方模型 |

| P1 / JD 推演题 | 线上任务大量失败，你如何处理？ | 故障应对、沟通 | 止损 → 定位 → 恢复 → 复盘 | 先暂停新任务或切换降级模型，避免继续扣费和堆积；通过 request ID、队列深度、Worker 心跳、第三方错误率和耗时定位问题。对未开始任务保留队列，对可恢复失败按策略重试，对已扣费但无产物的任务补偿。恢复后统计影响范围，并补充告警、回归用例和故障文档。我的项目已有健康检查、结构化错误、审计和按 Agent 的 Token/耗时记录，可以支撑类似定位。 | 如何告知用户？是否自动退款？ | 一上来重启所有服务；删除失败任务掩盖问题 |
| P1 / JD 推演题 | 你希望入职后三个月做到什么？ | 成长、可落地性 | 30/60/90 天 | 第一个月熟悉现有 Django 模型、生成链路、部署和线上问题，独立交付一个后台或任务接口；第二个月承担一段完整生成链路，补充状态、重试和监控；第三个月基于数据推动一次效果或稳定性优化。我不会一入职就重构全部架构，而是先建立业务理解和可信交付，再把 Agent 编排、评测和观测经验带进来。 | 第一个模块选什么？如何衡量？ | “三个月重构整个平台”；只谈学习不谈产出 |
| P1 / 相似题迁移 | 你独立项目多，如何适应团队协作？ | 协作风险 | 用工程规范证明可协作 | 独立开发让我能够承担端到端责任，但我也知道团队项目更重视接口边界和可维护性。我会通过需求确认、技术方案、分支和小 PR、代码评审、测试、变更记录和上线复盘协作。遇到分歧时先对齐目标和约束，用数据或最小实验验证，而不是坚持个人偏好。新团队里我会优先遵守已有规范，再提出渐进式改进。 | 被否决怎么办？如何估时？ | “我一个人效率更高”；贬低沟通和评审 |
