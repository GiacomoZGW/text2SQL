# 联邦 Text2SQL 项目：面试核心问答

> 适合手机阅读与面试前复习。所有回答围绕同一个项目：基于 LangGraph 的多 Agent 联邦 Text2SQL 系统，后端为 FastAPI，查询层使用 DuckDB，并已 Docker 容器化部署。

## 30 秒项目总述

我独立实现了一个联邦 Text2SQL 系统。用户用自然语言提问后，系统会经历意图识别、会话记忆与 Schema 检索、SQL 生成、只读与权限校验、语义审查、执行和结果分析。工作流由 LangGraph 编排，FastAPI 提供接口，DuckDB 用于多源联邦查询；同时加入 Token/耗时可观测、统一异常处理、任务队列与 Docker Compose 部署能力。重点不是让模型直接“写一条 SQL”，而是让整个链路可控、可追踪、可恢复。

---

## 1. 为什么要拆成多 Agent？

**可直接回答：**

Text2SQL 不是一次模型调用能稳定完成的任务。它至少包含理解问题、找对数据表、生成 SQL、做安全校验、执行以及解释结果这几个能力，而每一步的提示词、输入和失败处理都不同。所以我按职责拆成多个 Agent：意图识别负责路由，Schema/Retrieval 负责缩小上下文，SQL Agent 只负责候选 SQL，Validator 和 Reviewer 负责把关，Executor 只在通过校验后执行，Analyst 负责把结果转换成业务语言。

这样做的收益是：每一步都能单独观察、替换和回退；出错时能定位在“找表错、生成错还是执行错”，而不是只看到最终答案不对。对于简单的帮助类问题，Supervisor 会直接路由到 Help 节点，不必走完整 SQL 链路，成本和延迟也更低。

**代码中的主链路：**

`intent → supervisor → semantic_memory → schema → retrieval → sql → validator → reviewer → executor → analyst`

实际图中还有 `security`、`clarification`、`help`、`data_source`、`schema_response` 等分支。

**追问：多 Agent 会不会更慢？**

会增加编排开销，因此我不让每个节点都调用模型：安全规则、SQL 预处理、状态更新尽量用确定性代码；Supervisor 对非查询问题短路；Schema 检索先压缩上下文；并通过 Token/耗时监控找出真正慢的节点。多 Agent 的目标不是堆模型调用，而是用少量、职责清晰的调用换取稳定性。

## 2. 为什么选 LangGraph？

**可直接回答：**

我选 LangGraph 的原因是这个场景本质上是有状态、带条件分支和有限重试的工作流，而不是线性 Chain。比如意图不明确时要转澄清；SQL 校验不通过时要回到生成节点；执行失败时要带着错误信息有限重试；复杂问题还可能暂停后等待用户补充。LangGraph 可以把这些节点、边、条件路由和共享 State 显式表示出来。

它还带来两点工程价值：第一，状态贯穿整个请求，每个节点不需要靠拼 Prompt 传递全部上下文；第二，流程可以追踪和中断，便于记录执行轨迹、恢复任务和定位问题。LangChain 在项目中主要提供模型和消息抽象，LangGraph 负责把流程编排成可控的图。

**追问：为什么不用普通 if/else？**

简单 Demo 可以，但分支、重试、暂停和状态一多，if/else 会变成难维护的嵌套流程。图结构让节点职责、跳转条件和终止条件都更清晰，也便于后续增加新数据源或审查节点。

## 3. RAG 是怎么做的？

**可直接回答：**

这个项目的 RAG 主要服务于 Schema，不是把全库文档直接塞给模型。系统先从当前数据源读取表、字段、类型、主外键等结构信息，将每张表组织成 Schema 文档；对文档做向量化并带上数据源标识、表名等元数据。用户提问时先检索最相关的表和字段，再把小范围 Schema 传给 SQL Agent。

默认实现使用 DashScope Embedding，检索时采用向量相似度，并保留词法兜底；Schema 变化时根据 catalog hash 失效并重建索引。这样比全量注入 Schema 更省 Token，也能减少模型引用不存在表或字段的概率。

**追问：为什么需要实时读 Schema？**

向量索引是为了快速召回，实时 Schema/目录是事实来源。执行前和语义审查时仍以当前数据源的表字段为准，避免因为索引过期而生成旧字段。

**边界：**

RAG 提升表字段召回，不保证 SQL 必然正确，因此后面仍需要规则校验、语义审查和数据库执行反馈。

## 4. SQL 是怎么校验的？

**可直接回答：**

SQL 校验做成了多层防线，而不是只靠 Prompt。第一层是规则预处理：清理 Markdown 代码块，只允许单条只读查询，拒绝 DDL/DML 和危险关键字，并限制或补充 `LIMIT`。第二层用 SQL Parser 做语法解析。第三层结合用户、租户、数据源、表和字段权限做访问控制。第四层是语义 Reviewer：检查表和字段是否真实存在、连接关系是否合理、聚合和分组是否匹配，并在需要时检查执行计划。通过后才交给 Executor。

| 层级 | 解决的问题 |
| --- | --- |
| 只读规则 | 阻断 `INSERT`、`UPDATE`、`DELETE`、`DROP` 等写操作 |
| 单语句与 LIMIT | 防多语句注入、控制返回数据量 |
| Parser | 发现基础语法错误 |
| RBAC / 租户策略 | 防越权访问表和敏感字段 |
| Schema / 语义审查 | 发现不存在字段、不合理 Join、聚合错误 |
| 执行反馈 | 用数据库真实错误做最终验证 |

**追问：只用正则过滤够不够？**

不够。正则适合做第一道快速拦截，但无法可靠理解嵌套 SQL、方言和权限语义。因此项目同时使用 Parser、Schema Catalog、权限策略和数据库执行反馈。生产环境还应使用只读数据库账号和网络隔离，做到应用层与数据库层双重约束。

## 5. SQL 错了怎么办？如何防死循环？

**可直接回答：**

我把失败分成两类。校验阶段失败，例如字段不存在、越权或不是只读 SQL，会阻止执行，并把明确的原因返回 SQL 生成节点，让模型只修正问题点。执行阶段失败，例如数据库方言差异或 Join 错误，会记录数据库错误摘要和当前 Schema，再进行有限次数的修正。

系统不是无限自我修复：`MAX_RETRIES` 当前设置为 2，同时状态中维护 `error_count`。超过上限、重复生成相同 SQL、或者问题本身缺少关键信息时，工作流转到 Clarification 或直接返回结构化失败原因和可行动建议。这样避免无意义循环、成本失控和用户长时间等待。

**追问：重试时传什么给模型？**

传最小必要信息：上一条 SQL、规范化错误摘要、允许使用的表字段和方言提示；不把完整内部堆栈或敏感数据原样交给模型。并记录每次尝试，方便判断是模型问题、Schema 问题还是数据源问题。

## 6. Agent State 里面保存什么？

**可直接回答：**

State 是一次请求的共享上下文，不等同于长期记忆。我会保存原始问题、用户和数据源标识、对话上下文、意图与置信度、Schema 检索结果、候选 SQL、校验结果、执行结果、错误计数和执行轨迹等。每个节点只读取自己需要的字段，并写回自己的产物，例如 Retrieval 写相关 Schema，Validator 写校验结果，Executor 写执行结果。

| 类别 | 示例字段 |
| --- | --- |
| 请求身份 | `request_id`、`user_id`、数据源/租户标识 |
| 用户上下文 | `user_query`、`conversation_context`、偏好、语义记忆 |
| 路由信息 | `intent`、`intent_confidence`、澄清问题 |
| 检索与生成 | `schema_context`、相关 Schema、候选 SQL、最终 SQL |
| 风险与结果 | 校验结果、执行结果、`error_count`、`execution_trace` |

长期会话偏好和历史摘要放在 Memory Store；请求内 State 放在工作流中。二者分离，可以减少 State 膨胀，也避免无关历史污染当前 SQL。

## 7. Token / 耗时监控怎么做？

**可直接回答：**

我把模型调用统一收敛到工作流的 `_invoke_llm` 封装，而不是让每个 Agent 自己调用模型。封装在调用前记录开始时间，调用后从模型响应的 usage metadata 或 response metadata 中提取输入、输出和总 Token，并计算耗时；无论成功还是失败，都通过 `record_llm_call` 写入可观测存储。

此外，每个 Agent 节点也会写执行事件，所以可以按 `request_id` 串起完整链路：哪个节点调用了模型、耗时多少、用了多少 Token、最终成功还是失败。后端提供观测汇总接口，前端 `TokenMonitor` 展示请求数、Token、平均耗时、按 Agent 聚合和时间线。

**为什么有价值？**

它能区分“模型慢、检索慢、数据库慢还是排队慢”，也能发现无效重试和 Prompt 膨胀。优化时我会先压缩 Schema 上下文、短路非查询问题、减少重复 LLM 调用，而不是盲目换模型。

**边界：**

部分模型或代理网关不一定返回精确 usage。此时系统会记录可获取字段，并可以结合输入输出字符数做估算；估算值必须和真实 Token 标记区分，不能混称为精确计费数据。

## 8. 异常处理如何设计？

**可直接回答：**

异常处理分三层。第一层是节点内预期错误：例如检索为空、SQL 校验失败、数据库执行异常，将它们转换为结构化状态或可理解错误，交给重试、澄清或正常响应分支。第二层是任务运行时：本地模式使用有界异步队列控制并发和排队，Redis Streams 模式支持持久化任务、消费者重试和暂停；队列满、超时、任务失败都会写入状态和事件。第三层是 FastAPI 全局兜底：统一处理参数校验、权限错误、HTTP 异常和未知异常，返回统一错误结构，并通过 `X-Request-ID` 关联日志与观测记录。

对于耗时任务，接口返回 `request_id`，前端可以轮询结果，也可以订阅 SSE 事件获取 `queued`、`running`、`completed`、`failed`、`paused` 状态。这样接口不会因为一次模型或数据库异常直接失去可追踪性。

## 9. 面试时应主动说明的边界

- “1.5 万条数据 3 秒内响应”是本地特定聚合场景的测试结果，不等同于生产并发 SLA。
- 当前系统用 RAG 缩小 Schema 上下文、用校验和执行反馈提高可靠性；不宣称能消除模型幻觉。
- Redis Streams 提供持久任务和重试能力，但仍应通过幂等键、去重和审计应对至少一次投递语义。
- Docker Compose 已覆盖 API、Worker、Redis 和 PostgreSQL 等本地部署组件；真实生产环境还需要密钥管理、监控告警、数据库只读账号和容量规划。
