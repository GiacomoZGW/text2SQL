# Text-to-SQL Business Impact / 成本收益审计

> 审计日期：2026-09-15  
> 范围：当前 `federated_text2sql_project` 代码、`resume-project-facts.md`、`resume-project-description.md` 与本地 `observability.db`。  
> 目的：量化相对人工找库、找表、写 SQL、排错和跨库合并的时间与成本收益；本文不修改正式简历。

## 审计结论

当前最有把握的业务价值链是：

```text
3,000+ 表 Schema
  → Schema RAG 只注入相关结构
  → Prompt Token 降低约 75%
  → 减少模型输入成本与上下文噪声

自然语言问题
  → 自动找源 / 找表 / 生成 SQL / 审查 / 执行 / 汇总
  → 替代重复人工步骤
  → 具体节省时间仍需人工基线与查询量

首次 SQL 失败
  → Reviewer 拦截 / 错误回流 / 重生成
  → 减少部分人工修 SQL
  → 现有开发日志可计算修复漏斗，但不能当正式生产指标
```

根据本人最新确认，**98%+ Text-to-SQL 测试准确率**和**约 15,000 条订单 / 3 秒**可以写入项目成果。四项指标均可进入候选库，但应按 JD 取舍：AI / LLM 版优先保留 3,000+ 表、Token 降低约 75% 和 98%+；Python 后端 / 数据处理版优先保留 15,000 条 / 3 秒。测试口径未补齐前，不将 3 秒扩展为包含 LLM 推理的端到端响应。

## 2. 可从日志 / 代码进一步计算的指标

### 2.1 Schema RAG、Token 与模型调用

代码直接证明：

- `llm_calls` 按请求、Agent 记录 `model`、`prompt_chars`、输入/输出/总 Token、延迟和状态；
- `context_budget` 事件记录各 Agent 上下文字符数、估算 Token、预算和被截断区段；
- `retrieval` 事件记录检索后表名、来源、上下文字符数及是否截断；
- 当前代码首次召回 4 张表，错误回流时最多扩展到 6 张；
- 当前日志中的 232 次 LLM 调用全部记录模型为 `deepseek-v4-flash`，Token 字段均非空。

本地观测库当前快照：

| 日志指标 | 当前值 | 可否作为正式业务指标 |
| --- | ---: | --- |
| 请求记录 | 103 | 否；混有测试、诊断和演示请求 |
| LLM 调用 | 232 | 否；同上 |
| 单次 LLM 调用平均输入 Token | 927.31 | 仅供排查 |
| 单次 LLM 调用平均总 Token | 1,248.53 | 仅供排查 |
| 进入 SQL 管线的有效日志请求 | 52 | 可做开发样本，不是正式 benchmark |
| 每个 SQL 请求平均 LLM 调用 | 约 4.19 次 | 可解释工作流成本结构 |
| 每个 SQL 请求平均输入 Token | 约 4,004 | 可做开发样本，不是 75% benchmark 的正式优化后均值 |
| 每个 SQL 请求平均总 Token | 约 5,357 | 同上 |

**现有日志不能直接给出优化前后平均 Token。** 原因是请求、LLM 调用和检索事件没有 `experiment_group`、`rag_enabled`、`schema_strategy` 或 benchmark run ID，无法区分“全量 Schema 基线”和“Schema RAG 优化组”。

如果暂时把当前开发日志中的平均输入 Token `O = 4,004` 视为与“降低 75%”同一测试总体，可得到一个**条件估算**：

- 隐含基线 `B = O / (1 - 75%) ≈ 16,017` 输入 Token/查询；
- 单查询节省 `S = B - O ≈ 12,013` 输入 Token。

这不是仓库可复现 benchmark，只能作为后续核对线索，不能直接写入简历或对外成本报告。

建议后续为每个 benchmark 请求增加：`benchmark_run_id`、`variant=full_schema|schema_rag`、`schema_table_count`、`retrieved_table_count`、`rag_enabled`，再按同一问题、同一模型做配对统计。

### 2.2 请求耗时

观测库可统计端到端 `requests.latency_ms`，当前 52 个进入 SQL 管线的开发/演示样本为：

- 平均约 20.61 秒；
- 中位数约 16.79 秒；
- 近似 P95 约 41.99 秒。

这些记录跨越不同开发阶段，包含不同数据源、重试与测试流量，不能与本人确认的“15,000 条 / 3 秒”合并，也不能作为正式系统 SLA。后者目前不知道是纯 SQL、跨库执行还是端到端 LLM 响应。

### 2.3 SQL Reviewer 与自动修复漏斗

代码和现有字段可计算：

- 是否进入 SQL 生成管线；
- Validator / Reviewer / Executor 的成功与失败事件；
- 每个请求的重试次数和最终技术状态；
- SQL 是否可执行；
- 人工提交的结果正确性和满意度（接口与字段已存在）。

当前 52 个 SQL 管线开发样本中：

| 开发样本指标 | 当前值 | 定义限制 |
| --- | ---: | --- |
| 首轮通过并执行 | 47 / 52，约 90.4% | 表示首轮未出现 Validator/Reviewer/Executor 失败，不等于结果正确率 |
| Reviewer 拦截请求 | 5 / 52，约 9.6% | 按出现至少一次 Reviewer failed 的唯一请求计数 |
| Reviewer 拦截事件 | 11 次 | 同一请求重试后可能再次被拦截 |
| 回流后自动执行成功 | 2 / 5，40% | 可视为当前样本的自动修复覆盖率 |
| 最终未成功请求 | 3 / 52，约 5.8% | 不等于人工介入率；日志没有记录后续是否人工修正 |

当前 `result_correct` 和 `user_satisfied` 均无有效样本，`sql_executable` 也只覆盖 22 条历史记录，因此不能从本地库验证 98% 准确率或计算最终人工介入率。

为了得到正式指标，建议增加或稳定填充：`first_pass_success`、`reviewer_rejection_count`、`auto_repair_attempted`、`auto_repair_success`、`human_intervention_required`、`human_fix_minutes`，并将开发、评估和生产流量分开。

### 2.4 DuckDB 联邦查询

代码直接证明 `federation.yaml` 配置了 3 个逻辑源别名，分别对应 MySQL、PostgreSQL 日志源和 ClickHouse；缺少远程 URI 时使用 SQLite 演示库。用户确认真实执行过远程跨库查询。

现有观测库记录了 24 个 `federated_demo` 请求，其中 10 个进入 SQL 管线并成功，但事件没有保存每个挂载源的 `mode=remote|demo`，因此无法证明这些日志请求实际跨了几个远程源，也无法从日志计算减少了多少次导出和合并。

可新增以下事件字段：`active_source_count`、`active_source_types`、`remote_source_count`、`cross_source_join_count`、`rows_scanned/returned`、`sql_execution_ms`。这也能把纯数据库耗时与 LLM 耗时分开。

### 2.5 Redis Streams 任务恢复

代码直接证明：

- `HSETNX` 以 request ID 建立任务，重复提交同一 ID 时返回已有任务，避免重复入队；
- API 与独立 Worker 解耦，Worker 使用 consumer group 消费；
- `XAUTOCLAIM` 可认领超过 idle 阈值的 pending 消息；
- 基础设施级失败按最大尝试次数重新入队；
- 任务 Hash 和结果设置 TTL。

业务价值可表达为：降低 Worker 进程异常造成请求永久丢失的风险；相同幂等键的重复提交不会创建第二个任务；未确认的 pending 消息可由 Worker 重新认领。

不要绝对表述为“请求永不丢失”或“Exactly Once”：Redis 本身故障、TTL 到期或 Worker 在外部副作用后尚未 ACK 都可能影响结果，整体更接近 at-least-once 恢复语义。

当前观测库没有记录 `xautoclaim` 次数、恢复耗时或重复执行次数，Redis 任务记录也按 TTL 保留，无法从 SQLite 历史库计算正式恢复率。建议补充 `task_reclaimed`、`task_retry`、`task_recovered`、`duplicate_submission` 与 `recovery_latency_ms` 指标。

## 4. 每项指标公式

### 4.1 Token 与模型成本

设：

- `B` = 优化前平均输入 Token；
- `O` = 优化后平均输入 Token；
- `r` = Token 降幅，当前本人确认约 `75%`；
- `P` = 每输入 Token 价格；
- `P₁M` = 每百万输入 Token 价格；
- `Qm` = 月查询次数。

```text
单查询节省输入 Token S = B - O
Token 降幅 r = (B - O) / B
已知 O 与 r 时：B = O / (1 - r)
已知 O 与 r 时：S = O × r / (1 - r)

单查询成本节省 = S × P
若价格按百万 Token：单查询成本节省 = S / 1,000,000 × P₁M
月度 Token 成本节省 = 单查询成本节省 × Qm
```

若不同 Agent 使用不同模型或价格，应按 Agent 分项求和，不能只套一个单价。

### 4.2 人工时间与人工成本

```text
人工完成耗时 = 理解业务 + 找数据源 + 找表字段 + 写 JOIN/SQL + 排错执行 + 汇总结果

单查询节省人工时间
= 人工完成耗时 - 系统人工介入时间

月度节省人工小时
= 单查询节省人工分钟 × 月查询量 / 60

月人工成本节省
= 月度节省人工小时 × 人工时薪
```

更准确的混合复杂度计算：

```text
月度节省人工小时
= Σ[(该复杂度人工耗时 - 该复杂度系统人工介入时间)
     × 该复杂度月查询量] / 60
```

注意：“系统人工介入时间”包括问题输入、必要澄清、结果复核和最终人工修正，不应只使用系统机器耗时。

### 4.3 SQL 生成、Reviewer 与自动修复

```text
SQL 首次生成成功率
= 首轮通过校验/评审并成功执行的查询 / 进入 SQL 管线的查询

Reviewer 拦截率
= 至少被 Reviewer 拦截一次的查询 / 进入 SQL 管线的查询

自动修复覆盖率
= 被系统回流并最终修复成功的首次失败查询 / 首次失败查询

自动修复成功率
= 自动修复后成功执行且结果正确的查询 / 发起自动修复的查询

人工介入率
= 最终需要人工修正的查询 / 总查询

最终结果正确率
= 经审核为正确的查询结果 / 已审核查询结果
```

“成功执行”与“结果正确”必须分开统计；当前代码已经分设 `technical_success`、`sql_executable` 与 `result_correct`。

### 4.4 联邦查询与人工步骤

```text
单次跨源流程节省步骤
= 传统查询/导出/合并/计算步骤数 - 系统人工操作步骤数

单次跨源分析节省时间
= 传统多库流程耗时 - 系统人工介入时间

月度避免导出次数
= 每次传统流程导出次数 × 月跨源查询量

月度避免人工合并次数
= 每次传统流程合并次数 × 月跨源查询量
```

### 4.5 任务恢复

```text
任务恢复成功率
= Worker 异常后被重新认领并最终完成的任务 / 被重新认领的任务

重复提交抑制率
= 返回既有任务的重复请求 / 使用相同幂等键的重复请求

任务丢失率
= 超过 SLA 且无终态结果的已接受任务 / 已接受任务

平均恢复耗时
= Σ(恢复完成时间 - 异常或 pending 起始时间) / 成功恢复任务数
```

## 5. 一页简历最多保留的 2 个指标

一页简历仍建议每个版本最多突出 2 个“成果指标”，其余数字可嵌入技术 Bullet：

- **AI / LLM 版**：Prompt Token 消耗降低约 75% + Text-to-SQL 测试准确率 98%+；3,000+ 表作为规模背景。
- **Python 后端 / 数据处理版**：约 15,000 条订单 / 3 秒 + 3,000+ 表；Token 与准确率按 JD 决定是否保留。

推荐组合表达：

> 构建面向 3,000+ 表的 Schema RAG，通过向量、关键词与元数据混合召回仅注入相关 Schema，使 Prompt Token 消耗降低约 75%。

补充成果表达：

> 通过双候选 SQL、确定性 Reviewer 与错误回流机制，测试中 Text-to-SQL 准确率达到 98%+。

> 基于 DuckDB 完成多源查询联调，测试中约 15,000 条订单数据处理耗时控制在 3 秒内。

## 6. 为什么选择这两个指标

- 二者属于同一因果链：3,000+ 表说明问题规模，75% 说明方案带来的直接资源收益；
- 能同时服务 AI 应用、Agent/RAG 和成本优化岗位关键词；
- 与当前代码中的实时 Schema、混合召回、4～6 表注入、上下文预算和 Token 观测机制一致；
- 98%+ 能直接体现 Text-to-SQL 结果质量，适合 AI / LLM 岗，但必须解释是 Exact Match、Execution Accuracy 还是人工审核准确率；
- 15,000 条 / 3 秒能体现查询处理性能，适合 Python 后端 / 数据处理岗，但必须限定执行边界、环境与缓存状态。

面试前仍必须补齐 75% 的测量口径；“适合保留”不等于“无需解释”。

## 8. 面试口径与追问准备

### 8.1 Schema RAG / Token

需要准备：

- 3,000+ 表如何统计，来自几个库；
- 全量 Schema 基线如何构造，是否会超过模型上下文；
- 75% 是 input token 还是 total token，使用哪个模型和多少个问题；
- 同一问题在基线组和 RAG 组分别多少 Token；
- 召回 4～6 表是否影响正确率，如何处理漏召回；
- embedding 失败时为何回退关键词+元数据排序。

安全口径：

> 3,000+ 表和约 75% Token 降幅是本人确认的测试结果；当前仓库保留了逐调用 Token 观测，但没有保留该次 A/B benchmark 标记，因此面试前需要把原始基线与问题集整理成可复述口径。

### 8.2 98% 准确率

高概率追问：测试集多大、SQL 是否唯一、错误类型如何分类、是否计算重试后结果、是否人工审核。

回答前必须选定准确率定义：

- Execution Accuracy：执行结果与期望结果一致；
- Exact Match：SQL 规范化后与标准 SQL 一致；
- Human Review Accuracy：人工按业务语义审核为正确。

不能只回答“执行成功率”；能执行的 SQL 可能返回错误业务结果。

### 8.3 15,000 条 / 3 秒

高概率追问：3 秒是否包含模型推理、跨几个数据库、什么 JOIN/聚合、冷启动还是 warm cache、硬件和 P95。

在口径未补齐前，安全表述为：

> 测试中约 15,000 条订单数据处理耗时控制在 3 秒内；该指标当前指查询处理性能，不表述为包含 LLM 推理的端到端响应。

### 8.4 人工时间收益

面试最好准备一个真实中等或复杂案例，按时间线说明：

1. 人工过去如何确认业务口径；
2. 去哪些库、找哪些表与字段；
3. 如何写 JOIN、导出和合并；
4. 总耗时与最容易出错的环节；
5. 系统现在需要多少人工输入、澄清和复核；
6. 每周发生多少次，最终折算多少小时。

不要把机器响应时间直接当人工节省时间。人工收益的核心是减少找 Schema、写 SQL、排错和跨库搬运，而不是单纯“3 秒返回”。

### 8.5 Redis Streams

需要准备一次真实恢复过程：如何制造或发生 Worker 异常、消息何时进入 pending、`XAUTOCLAIM` 由谁触发、重试多少次、最终是否重复执行。

安全口径：

> 通过 request ID 幂等入队、Consumer Group 与 pending claim 降低 Worker 异常导致任务丢失的风险；系统采用可重放的 at-least-once 恢复思路，并非严格 exactly-once。

## 9. 分岗位 Business Impact 版本
